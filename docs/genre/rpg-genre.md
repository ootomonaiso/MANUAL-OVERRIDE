# RPG（ローグライク戦闘）ジャンル設計文書

> **本文書のステータス: 設計のみ・未実装**
> `rpg` は現状 `exp` を拾ってもスコアが増えるだけで、レベルアップ・ステータス成長が一切存在しない（`player.level` フィールドは [entities.ts:29](../../src/game/entities.ts#L29) に存在するが誰も参照していない死んだフィールド）。`enableFeatures` も `dungeon` と完全一致しており、ジャンルとしての固有性がない。
> 本文書は、あるべき姿として**ローグライク戦闘に絞ったRPG**へゼロから再設計したもの。実装前提のコード変更は含まない。**実装が完了したら、この文書を「現状の実装を記録する」形式（`tetris-genre.md` 等と同じ体裁）に書き直すこと。**

## 概要

マップ探索は作らず、**戦闘のみ**を繰り返すローグライクRPG。敵が出現 → プレイヤーが行動を選択 → 撃破 → 3択からスキルを1つ獲得（ドラフト）→ 次の敵、のループを繰り返す。スキルの重複取得によるレベルアップと、物理/魔法の属性相性が駆け引きの核。

## アーキテクチャ上の最大の変更点

他の21ジャンルは全て「同じ横スクロールCanvasエンジン（`SideScroller`）のルール変奏」だが、本ジャンルは**ジャンル確定後、横スクロールCanvasを使わず戦闘専用のターン制UIへ完全移行する**唯一の例外になる。マップ・移動・ジャンプ・障害物回避は行わない。

これに伴い、既存の `GenrePlugin`（Canvas描画委譲）・`FeatureSystem`（`preUpdate`/`update`/`render` によるフレーム単位処理）という前提そのものが `rpg` には当てはまらない可能性が高い。実装時は以下のいずれかの方針を選ぶ必要がある。

- **A. 既存の phase マシン（`title → tutorial → ... → genreLocked → throwing`）はそのまま使い、`genreLocked` 後の描画だけ Canvas から専用の戦闘UI（Vueコンポーネント）に差し替える**
- **B. 戦闘専用の新しい phase を追加する**

いずれにせよ `useGameState.ts` の phase 管理・`App.vue` の画面切り替えに手を入れる、他ジャンルにない特別対応が必要。

## ゲームループ

```
戦闘開始
  │
  ▼
敵が出現（enemies/*.json から選出）
  │
  ▼
プレイヤーのターン ── 行動選択（アクティブスキル1〜4 or 通常攻撃「叩く」）
  │                     └ 選択したスキルのクールタイムをセット
  ▼
効果解決（ダメージ計算 = 属性相性 × ステータス、命中判定、クリティカル判定）
  │
  ▼
敵のターン ── enemies/*.json の行動パターン配列に従い順にスキルを使用（ループ）
  │
  ▼
全アクティブスキルのクールタイムを1減算
  │
  ├─ 敵のHPが0 → 撃破 → スキルドラフト（3択）→ 次の敵へ
  └─ 敵のHP>0 → プレイヤーのターンへ戻る
```

## ステータス（9種）

| 区分 | 項目 | 内容 |
|---|---|---|
| 基本6種 | `HP` | 体力 |
| | `STR` | 物理攻撃力 |
| | `DEF` | 物理防御力 |
| | `INT` | 魔法攻撃力 |
| | `REF` | 魔法防御力 |
| | `AGI` | 速度（行動優先順位、一部スキルの効果参照元） |
| 追加3種 | `命中率` | 攻撃が当たる確率 |
| | `クリティカル率` | クリティカル発生確率 |
| | `クリティカルダメージ倍率` | クリティカル時の追加倍率 |

プレイヤー・敵の双方が同じ9ステータスを持つ。パッシブスキルは基本的にこれらのステータスを上昇させる効果を持つ（一部例外あり）。

## アクティブスキル

- 専用の**アクティブスキル枠を4つ**持つ。スキル1は初期状態で「叩く」（無属性の通常攻撃）が固定でセットされている。スキル2〜4は初期は空
- 使用には**ターンを1消費**する（＝そのターンは他の行動ができない）
- クールタイムは0以上の整数。使用すると設定され、**タームごとに1ずつ減少**する（0で再使用可能）
- 属性（物理／魔法／無属性）を持つ。無属性のアクティブスキルは基本的にサポート系（バフ・デバフ・回復等、直接ダメージを持たない）

## パッシブスキル

- ターンを消費せず、**常に効果が適用される**
- アクティブスキル枠を**埋めない**（別枠管理）
- 基本的に9ステータスのいずれかを上昇させる効果。特殊な効果を持つものも許容する

## スキル獲得（撃破後のドラフト）

敵を倒すと**3つの選択肢**が提示され、1つを選んでスキルを獲得する。

- **アクティブスキルを選んだ場合**: 空いているアクティブスキル枠にセットされる
- **アクティブスキル枠が全て埋まっている場合**: 新規のアクティブスキル（＝まだ枠にセットされていない種類）は選択肢に出現しなくなる。**既に持っているアクティブスキルと同種**のものだけが選択肢候補になり得る（＝重複取得によるレベルアップ狙いの選択肢になる）
- **パッシブスキル**: 枠を消費しないため、常に選択肢候補になり得る
- **例外（打ち止め時）**: レベルが上限まで上がりきり、かつ獲得できるスキル（新規・重複とも）が尽きた場合、代わりに**基本6ステータスのいずれかをランダムに微増させる**選択肢を表示する（3択の穴埋め用フォールバック）

## スキルレベルアップ（重複取得）

同じスキルを重複して取得すると、そのスキルのレベルが上がる。必要な重複取得数は次の通り（取得のたびにスタックが1つ消費される）。

| レベル遷移 | 必要な重複取得数 | 累計取得回数（初回含む） |
|---|---|---|
| Lv1（初回取得） | ― | 1回目 |
| Lv1 → Lv2 | 1個 | 2回目 |
| Lv2 → Lv3 | 3個 | 5回目 |
| Lv3 → Lv4（MAX） | 5個 | 10回目 |

効果量はレベルごとに**2のレベル乗**で増加する（例: Lv1を基準倍率とすると Lv2は2倍、Lv3は4倍、Lv4は8倍 ── 正確な式は実装時に確定させる。「基準×2^(レベル-1)」か「基準×2^レベル」かは未確定）。

トレードオフ: 1つのスキルを重複取得してレベルを上げるということは、その回のドラフトで**他の新規スキルを取る機会を1回失う**ことを意味する。強力だが選択の幅を犠牲にする、という一長一短の設計。

## 属性システム

- 属性は**物理**と**魔法**の2種類（＋無属性）
- プレイヤー・敵は、ある属性に対して「弱点」「耐性」「無し（等倍）」のいずれかのステータス効果を持ちうる
  - 弱点属性で攻撃された場合: ダメージ **2倍**
  - 耐性属性で攻撃された場合: ダメージ **半減**
  - 何も持たない場合: **等倍**
- 敵の攻撃（アクティブスキル）は物理・魔法・無属性のいずれか
- プレイヤーのアクティブスキルも同様に物理・魔法・無属性のいずれか
- 無属性のスキル・攻撃は、基本的にサポート系（直接ダメージを持たない、バフ・デバフ・回復など）に振られる。この規約はプレイヤー側・敵側の双方に共通

## 敵定義（データ設計）

敵は種類ごとに1ファイルのJSONで管理する（`src/data/enemies/{enemy-id}.json` 想定）。

```json
{
  "id": "example_enemy",
  "label": "サンプル敵",
  "stats": { "hp": 30, "str": 8, "def": 4, "int": 2, "ref": 3, "agi": 5, "hitRate": 0.9, "critRate": 0.05, "critDamageMultiplier": 1.5 },
  "resistance": { "physical": "weak", "magical": "none" },
  "activeSkills": ["skill_bite", "skill_roar"],
  "passiveSkills": ["passive_thick_hide"],
  "actionPattern": ["skill_bite", "skill_bite", "skill_roar"]
}
```

- `resistance`: 属性ごとに `weak`（弱点）/ `resist`（耐性）/ `none`（無し）
- `actionPattern`: 敵の行動パターンを表す配列。**基本的にループ**し、配列の順番通りにスキルを使用する（ランダムではなく決定的な行動パターン）

## スキル定義（データ設計）

スキルは1スキル1ファイルのJSONで管理し、**いつでも数を増やせる**構成にする（`src/data/skills/{skill-id}.json` 想定。`sfx/*.json` と同じ「JSON追加だけで拡張できる」流儀）。

```json
{
  "id": "skill_strike",
  "label": "叩く",
  "kind": "active",
  "element": "none",
  "cooldown": 0,
  "effect": { "type": "damage", "power": 5 }
}
```

```json
{
  "id": "passive_iron_will",
  "label": "鉄の意志",
  "kind": "passive",
  "effect": { "type": "statBoost", "stat": "def", "amount": 2 }
}
```

## 状態管理

プレイヤーが**現在所持しているスキルの状態**（アクティブ4枠それぞれのスキルID・レベル・重複スタック数・現在のクールタイム、および所持パッシブスキルとそのレベル一覧）を保持する必要がある。既存の `player`（`Player` クラス, [entities.ts](../../src/game/entities.ts)）を拡張するか、`useBattleState.ts` 側で独立した `BattleState` として持つかは実装時に決定する。

## 実装上の注意点

1. 本ジャンルは他ジャンルと異なり「横スクロールCanvasの変奏」ではなく「戦闘専用UIへの完全移行」になる。`useGameState.ts` の phase 管理・`App.vue` の画面切り替えロジックに、他ジャンルにない特別分岐が必要になる（詳細は「アーキテクチャ上の最大の変更点」参照）。
2. スキルレベルの効果倍率の正確な式（`基準 × 2^(レベル-1)` か `基準 × 2^レベル` か）は未確定。実装時に確定させる。
3. クールタイムの減算タイミング（プレイヤーのターンのみで1減算か、敵のターンも含めた1ラウンドで1減算か）は本文書時点で厳密には未確定だが、「ターンごとに1ずつ減る」という記述から、1ラウンド（プレイヤー行動+敵行動）につき1減算という解釈で設計している。異なる場合は実装時に修正する。
4. `rpg` と `dungeon` は現状 `enableFeatures` が完全一致した複製ジャンルだが、本設計により `rpg` が独自の戦闘システムを持つことで重複は解消される。`dungeon` 側（アクション探索寄りの現行仕様のまま残すか、別途再設計するか）は本文書のスコープ外。
5. スキル・敵のJSON定義は「後から数を増やすだけで拡張できる」ことが要件のため、`framework/ConfigLoader` 側のディレクトリ自動読み込みの仕組み（`src/data/cards/*.json` や `src/data/sfx/*.json` と同様の一括ロード）を流用する設計にすること。
