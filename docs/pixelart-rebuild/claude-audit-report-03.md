## C-01: `ellipse()` の縦方向が最大 1.5 倍に膨張する【高】

### 症状

`ellipse()` に小さい `ry` を渡すと、**指定より縦に大きく描かれる。**

実測（`PIXELART.size = 4`、オフスクリーン canvas の画素を計測）:

| 呼び出し | 期待する高さ | 実測の高さ | 倍率 |
|---|---|---|---|
| `ellipse(cx, cy, 14, 3, …)` | 6px | 8px | 1.33× |
| **`ellipse(cx, cy, 14, 4, …)`** | **8px** | **12px** | **1.5×** |
| **`ellipse(cx, cy, 20, 4, …)`** | **8px** | **12px** | **1.5×** |
| `ellipse(cx, cy, 8, 2, …)` | 4px | 4px | 1.0× |

**横幅はいずれも正確**（28px / 40px / 16px）。縦だけが膨らむ。

### 影響範囲

`ry = 4` は**キャラクターの足元の影**で使われている実値である。

```
src/genres/ArenaPlugin.ts:110        px.ellipse(w / 2, h + 2, w * 0.38, 4, 'rgba(0,0,0,0.35)')
src/genres/BasePlugin.ts:80          px.ellipse(w / 2, h + 2, w * 0.4,  4, 'rgba(0,0,0,0.25)')
src/genres/BulletRunnerPlugin.ts:128 px.ellipse(w / 2, h + 2, w * 0.4,  4, …)
src/genres/DungeonPlugin.ts:128      px.ellipse(w / 2, h + 2, w * 0.36, 4, …)
src/genres/HackSlashPlugin.ts:120    px.ellipse(w / 2, h + 2, w * 0.38, 4, …)
src/genres/PlatformerPlugin.ts:105   px.ellipse(w / 2, h + 2, w * 0.4,  4, …)
src/genres/RacingPlugin.ts:103       px.ellipse(w / 2, h + 3 - wheelBounce, w * 0.42, 4, …)
src/genres/SurvivalPlugin.ts:111     px.ellipse(w / 2, h + 2, w * 0.38, 4, …)
src/genres/AquaticPlugin.ts:130      px.ellipse(w / 2, h + 2, w * 0.38, 3, …)   ← 1.33×
```

**該当 9 プラグイン全ての影が、意図の 1.33〜1.5 倍の厚さで描かれている。**
影は接地感を与える要素であり、厚すぎるとキャラクターが浮いて見える。

### 原因

`_snapSize()` が**最低 1 セル（4px）を保証する**ことにある。

```ts
function _snapSize(v: number, size: number): number {
  return Math.max(size, Math.ceil(v / size) * size)   // ← 最低 1 セル
}
```

`ellipse()` は行の高さを `rowH = (ry * 2) / steps` で求める。
`ry = 4` のとき `steps = max(3, round(8 / 2)) = 4`、`rowH = 8 / 4 = 2`。
**`rowH` が 1 セル（4px）を下回るため、各行が 4px に引き伸ばされる。**
本来 2px の行が 4px になり、行同士のスナップ位置の重なり方次第で
全体が 8px → 12px に膨らむ。

これは `ellipse` 固有ではなく、**内部の行・列の刻みが 1 セルを下回る全プリミティブ**
（`circle` の小半径、`tri` の低い三角形、`_annulus` の薄いリング）に共通する構造的欠陥である。

`circle()` でも `r = 1` で直径 2px → 4px（2×）、`r = 3` で 6px → 8px（1.33×）を確認した。
ただし `circle` は `r ≥ 4` で正確になるため、実害は `ellipse` の影ほど広くない。

### 対処方針

R-01 の「セル整数演算への切り替え」で同時に解消できる。
半径をセル数へ量子化してから整数演算で行を生成すれば、
**1 セルを下回る刻みがそもそも発生しない。**

ただし注意点がある。`ry = 4`（= 1 セル）の影を整数化すると
**縦 1 セル（4px）の平たい影**になり、現在の見え方より薄くなる。
`ry` の値自体を調整する必要が出る可能性があるが、
**これらの値は変換前から存在する既存値**であり、
「色・数値を変更しない」という要領書の前提に触れる。
**実装時にユーザー判断を仰ぐこと。**

## C-02: `circle()` が左右非対称【高】

### 症状

`circle(200, 200, 40, …)` を描いた実測値:

| 項目 | 実測 |
|---|---|
| 左端 | x = 160（中心から **40px**） |
| 右端 | x = 239（中心から **39px**） |
| 鏡映軸 x=199.5 での非対称画素数 | **128 px** |
| 鏡映軸 x=200 での非対称画素数 | **144 px** |
| 上下の非対称画素数 | **0 px** |

**上下は完全対称だが、左右が 1px ずれている。**

### 原因

各行を `rect(cx - halfW, …, halfW * 2, …)` で描いており、
`_toDevice()` が**左端は `_snapPos`（四捨五入）、幅は `_snapSize`（切り上げ）**
と異なる規則で丸めるため、右端 = 丸めた左端 + 切り上げた幅 となり、
中心に対して対称にならない。

上下が対称なのは、行の生成が `yTop = -r + i * rowH` と
中心対称な式になっているためである。

### 補足: R-01 との関係

独立監査および §11 R-01 は「半径変化時の組み替え」を指摘していた。
本監査でこれも実測で再確認した。

```
r = 30.0 〜 31.2 を 0.1 刻みで変化させたときの行数:
  15, 15, 15, 15, 15, 15, 15, 15, 15, 15, 16, 16, 16
                                          ↑ ここで全行境界が組み替わる
```

**C-02（左右非対称）は R-01 とは別の症状**であり、
R-01 の対処（整数化）で同時に解消されるが、
検証項目としては**対称性を独立に確認する必要がある。**

## C-03: `arcBlocks()` の重複描画で半透明時に輝度ムラ【中〜高】

### 症状

`arcBlocks(cx, cy, 40, 0, 2π, …, 1)` で全周を描いた実測:

| 項目 | 実測 |
|---|---|
| 発行した `fillRect` 数 | 64 |
| 実際のユニークセル数 | 58 |
| **重複描画されたセル** | **6** |

不透明で描く分には同色の重ね塗りなので見た目に影響しない。
しかし **`globalAlpha = 0.5` で描くと、重複セルだけ二重合成される。**

```
出現したアルファ値: 128, 192
  → 128 = 0.5 の 1 回合成
  → 192 = 0.5 の 2 回合成（重複セル）
判定: ❌ 弧の上に明るい斑点が出る
```

### 影響範囲

**`arcBlocks` は半透明の文脈で実際に使われている。**

```
src/game/systems/SurvivalFeature.ts:270-277
  px.withAlpha(fadeAlpha, () => {          ← 半透明スコープの内側
    px.halo((expand, c) => {
      px.arcBlocks(cx, cy, range + expand, …)   ← ハローも半透明
      …
    })
    px.arcBlocks(cx, cy, range, …)
  })
```

近接攻撃の斬撃エフェクトは**フェードしながら描かれる**ため、
弧の上に不均一な明点が乗る。`PuzzleFeature.ts:503-504, 527` のゴールリング・
駒の輪郭でも同じ経路を通る（`AquaticPlugin.ts:108` の珊瑚は不透明のため影響なし）。

### 原因

弧長から求めたステップ数で角度を等分し、各サンプル点に `t × t` の矩形を置いている。

```ts
const steps = Math.max(1, Math.round(arcLen / s))
for (let i = 0; i <= steps; i++) { … this.rect(px - t/2, py - t/2, t, t, color) }
```

サンプル間隔は**弧に沿って** `s` だが、スナップ後のセル位置は
弧の傾きによって同一セルに落ちることがある（特に弧の上下端・左右端の付近）。
また `i <= steps` としているため全周では始点と終点が重なる。

### 対処方針

描画済みセルを `Set` で記録し、**同一セルを 2 回描かない**ようにするのが最小の修正。
セル座標は `_toDevice()` の結果から得られるため、`arcBlocks` 内で完結できる。

## C-04: 未解決の動的色スロットで警告が出ない【中・仕様違反】

### 仕様

要領書 §5「異常系」は次のとおり規定している。

> | パレットに `@` キーがあるのに `slots` に対応する値が無い | そのセルを**透明として扱う**（描かない）。**DEV で `console.warn`** |

### 実装

```ts
// src/game/render/SpriteRenderer.ts:73
if (color === null) continue // 未解決の動的色スロット → 透明として扱う
```

**透明として扱う挙動は仕様どおりだが、`console.warn` が無い。**

### 実測

`slots` を空にして `player_base` を描画した結果:

| 項目 | 実測 |
|---|---|
| 戻り値 | `true`（成功扱い） |
| 描画された画素数 | 966 px（欠落したまま描画される） |
| **警告の数** | **0** |

**スプライトが穴あきのまま静かに描画され、開発者に何も伝わらない。**
`id` が存在しない場合は `_warnedMissingId` で警告する実装があるのに、

スロット名の綴り間違いや `slots` の渡し忘れは起こりやすい。

実際、本ブランチの実装がこれまで気づかれずに来たこと自体がその証左になっている。

## C-05: `line()` が仕様の Bresenham ではなく DDA【低・仕様違反】

### 仕様と実装の食い違い

要領書 §4 は次のように規定している。

> `/** Bresenham によるブロック線（stroke の代替）。thickness はセル単位（§3） */`

実装は Bresenham ではなく、**弧長を等分する DDA（線形補間サンプリング）**である。

```ts
const steps = Math.max(1, Math.round(dist / s))
for (let i = 0; i <= steps; i++) {
  const px = x0 + (dx * i) / steps      // ← 線形補間。Bresenham の整数増分ではない
  const py = y0 + (dy * i) / steps
  this.rect(px - t / 2, py - t / 2, t, t, color)
}
```

これは **R-01 と同種の「アルゴリズムレベルの仕様違反」**である。

### ただし表示上の欠陥は確認できなかった

R-01 と異なり、**実測では問題が出なかった。** 憶測で欠陥と書かないため、実測値を残す。

| 検証 | 結果 |
|---|---|
| 水平線のセル間隔 | 4px で完全に等間隔、重複 0 |
| 4 通りの角度での途切れ（空き列） | いずれも **0** |
| 端点を 0.1 刻みで動かしたときのセル数 | **25 で一定**（組み替えなし） |

**したがって C-05 は「表示は正しいが、要領書の記述と実装が一致していない」問題である。**

### 対処方針

2 つの選択肢がある。**どちらもユーザー判断が必要。**

| 案 | 内容 | 評価 |
|---|---|---|
| **A** | 要領書の記述を実装に合わせる（「Bresenham」→「弧長等分サンプリング」） | 表示に問題がない以上、**こちらを推奨。** 動いているコードを書き換えるリスクを負わない |
| B | 実装を Bresenham に書き換える | 47 箇所の `px.line()` 呼び出しすべてに影響。表示上の利益は確認できていない |

**ただし A を選ぶ場合、「要領書に合わせて実装を直す」のではなく
「実装に合わせて要領書を直す」ことになる点に注意が必要である。**
R-01 では逆の判断（実装を仕様に合わせる）をしており、
**判断の一貫性についてユーザーの確認を得るべきである。**

## C-06: `block()` の陰影量がハードコード【低・規約違反】

```ts
// src/game/render/PixelCanvas.ts:333-334
const light = _lighten(base, 40)
const dark = _lighten(base, -40)
```

`40` は明暗の強さを決める**視覚チューニング値**である。

`CLAUDE.md`「マジックナンバー」は次のとおり定めている。

> - ソースコード内に数値リテラルを直書きしない
> - ゲームバランス値 → `src/data/config/*.json` に定義して `tunables.ts` 経由で参照
> - 実装固有の閾値 → ファイル先頭の `const` 定数として定義

`40` は JSON にもファイル先頭の定数にもなっていない。
`pixelart.json` に `blockShadeAmount` として追加するのが素直である。

**`PixelCanvas.ts` は本ブランチで新規作成されたファイルであり、
この値は変換作業で新たに持ち込まれたものである**（既存コードからの移植ではない）。

同様に `1e-6`（変換行列の判定に使う epsilon、3 箇所）も
ファイル先頭の `const` にすべきである。こちらは実装固有の閾値にあたる。

## C-07: ディザ行列のコメントが実体と一致していない【低】

```ts
// ── 4x4 Bayer 行列によるオーダードディザ ───────────────────────────
const _BAYER_2X2 = [
  [0, 2],
  [3, 1],
]
```

**コメントは「4x4」、変数名と実体は 2x2。**

実測でも 2x2 周期であることを確認した。

```
dither(0, 0, 32, 32, '#000', '#fff', 0.5) の上位 4x4 セル:
  BABA
  ABAB
  BABA
  ABAB
  → 2x2 周期
```

変数名 `_BAYER_2X2` と実体は正しいので、**コメントだけが誤り。**
`ratio` の段数が `ditherRatioSteps = 4` であることと混同した可能性がある。

なお 2x2 Bayer は 4 段階の閾値しか持たないため、
`dither` で表現できる濃度は実質 4 段階である。
`ditherRatioSteps = 4` と整合しており**機能上の問題はない。**

## C-09: `_toDevice()` の外接矩形算出が 2 隅のみ【潜在・現時点では実害なし】

```ts
const x0 = x, y0 = y, x1 = x + w, y1 = y + h
const p0x = m.a * x0 + m.c * y0 + m.e
// … p0 と p1 の 2 点のみから外接矩形を作る
```

回転を含む変換で正しい外接矩形を得るには**4 隅すべて**を写す必要がある。
2 隅のみの算出は、軸平行および 90° の倍数の回転では数学的に正しいが、
**任意角度では誤る。**

検算（45° 回転、`rect(0, 0, 10, 10)`）:

```
実装の算出:  p0 = (0, 0), p1 = (0, 14.14)  → 幅 0（!）
正しい値:    幅 14.14
```

### 現時点では実害がない

実使用箇所を全数確認した結果、`ctx.rotate()` は**1 箇所のみ**である。

```
src/game/sideScroller.ts:989    ctx.rotate(-Math.PI / 2)
```

`-90°` は 90° の倍数であり、2 隅算出でも正しい結果になる
（対角の 2 隅が外接矩形の対角に写るため）。`HackSlashPlugin.ts:134-137` の剣は
`ctx.rotate` ではなく座標を自前で回して `px.line` に渡しており、変換行列は回転しない。

**したがって現在は正しく動作している。**
ただし将来「45° に傾いた敵」「回転する障害物」などを追加した瞬間に破綻するため、
**潜在的な罠として記録する。** 修正するなら 4 隅の min/max を取るだけで済む。
